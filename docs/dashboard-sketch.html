dualbootautomationproject · design sketch

Flight Deck

A 2560 × 720 touch ribbon that boots the workstation into Windows or Linux, launches the sim, and shows what all three machines are doing — driven by the Raspberry Pi, so it still works when the workstation is off.

Corsair Xeneon Edge 14.5″ Raspberry Pi 5 Windows + Linux workstation Mac mini Prometheus · Grafana · Loki

The premise

The Pi already runs the boot logic. Give it a screen.

The repo today has one front-end: an Echo turns on a fake Wemo plug, fauxmo fires flightsim-boot.sh, and the script wakes, reboots, or launches into the right OS. The Xeneon Edge is a second front-end onto the same machinery — plus the thing voice can never give you, which is a live picture of what's happening during the ninety seconds after you ask.

It has to hang off the Pi, not the workstation. The workstation is the subject of every control on this screen; a panel that goes black exactly when you reboot the machine is the one thing this can't be. The Edge takes HDMI 2.0 alongside USB-C DP-alt, and its touch panel is a standard USB HID digitizer — so a Pi 5 drives it with a micro-HDMI cable for video and a USB-A cable for touch, with no vendor software in the path.

The ribbon

2560 × 720 — drawn at true proportion

Five-to-one is a strange canvas: almost no vertical room, enormous horizontal room. That argues for three fixed columns rather than a scrolling page — act on the left, context in the middle, fleet on the right — and for never hiding the boot controls behind a tab. At 14.5″ this panel is ~180 ppi, so a 44 px target is a 6 mm one. Everything touchable here is 158 px or larger.

Control plane

One boot path, two front-ends

deck-api surface

EndpointDoesNotes
GET /api/stateEverything the UI renders in one object: workstation OS, uptime, boot-in-flight phase, per-host rollups.Cheap enough to poll; SSE is the real path.
GET /api/eventsServer-sent stream of state deltas.Phase changes push instantly — no 5 s polling lag mid-boot.

Same trust model as the existing boot agent: bound to the LAN, shared-token guarded, no credentials stored. The kiosk browser talks to it over loopback and needs no token at all.

Boot progress

Seven phases, each with something that actually reports it

Known dead end

WOL cannot select a GRUB entry. From full off the machine always lands in the saved default, so “cold boot straight into Windows” costs a chained second reboot unless you flip the default — and flipping it breaks the Windows → Linux leg entirely. The panel should show “+1 reboot” on the tile rather than pretending both are equally fast.

Metrics plane

The collector cannot live on the machine that reboots

Storage, not optional

Prometheus at a 15 s scrape across six targets writes continuously. On a microSD card that is a dead card in months. This needs an NVMe HAT or a USB-SSD boot on the Pi before anything else in this section gets built.

Two things dual-boot breaks

Label it so the timeline survives

Scrape Windows and Linux with the same instance="workstation" and a distinguishing os label, not as two unrelated hosts. Then one CPU panel reads continuously across a reboot instead of two half-empty graphs. Set Connect null values: never so the gap where neither OS was up stays visible — that gap is real information.

Don’t alert on a normal reboot

up{job="windows"} == 0 fires every single time you boot into Linux. The condition that means something is neither OS answering for longer than a boot takes: alert on absent() over the union of both jobs with a 10 minute for:, and let the boot orchestrator publish its own flightdeck_boot_in_flight gauge to suppress it outright.

Hardware

What plugs into what

LinkCableNote
Pi 5 → Edge (video)micro-HDMI → HDMIUse HDMI0 (the port nearest USB-C). The Pi’s USB-C is power-only — no DP-alt.
Pi 5 → Edge (touch)USB-A → USB-CEnumerates as a HID digitizer; no driver, no iCUE.
Edge powerUSB-C PD supplyVerify on arrival. Give it its own supply rather than drawing from the Pi, which is already budgeting for NVMe.
Pi storageNVMe HAT or USB SSDNon-negotiable once Prometheus is on it.

On the software side: force the mode with video=HDMI-A-1:2560x720@60 in cmdline.txt if the EDID doesn’t offer it, then run the UI under cage (a Wayland kiosk compositor) rather than a full desktop — one fullscreen surface, no panels, no screen-blanking to fight. Brightness is controllable over DDC/CI via ddcutil for a scheduled evening dim, with wake-on-touch.

Build order

Each phase is usable on its own

  1. Bring the panel up

    Edge on the Pi at native resolution, touch calibrated, cage + a browser showing a placeholder page on boot. Nothing here depends on the rest, and it de-risks the one unknown in the whole plan.

  2. deck-api and the v1 UI

    The service, the state file, SSE, and the four boot tiles with live phase tracking. Repoint fauxmo’s on_cmd at it. At the end of this phase the screen fully replaces the voice trigger.

  3. Prometheus, Grafana, and the core dashboards

    Pi on NVMe, exporters on Windows/Linux/Pi, blackbox probes, and the five phase-2 dashboards. The Edge gains its metrics tabs.

  4. Mac mini, boot telemetry, and the greeting hook

    Apple-Silicon exporters, boot events published as metrics and Grafana annotations, and the callback that makes phase 7 real. Loki for the boot and agent logs.

  5. Polish

    Frametime capture and the sim-session dashboard, alerts to the phone, scheduled dimming, hold-to-confirm on the destructive verbs, and a shutdown path.

Five things I need from you

Each one changes the build

  • Mac mini — Apple Silicon or Intel? It changes the exporter set completely; Intel gets usable SMC temps, Apple Silicon needs the macmon path.
  • Pi model and storage. A Pi 4 on microSD will drive the screen but shouldn’t host Prometheus; a Pi 5 with NVMe does both comfortably.
  • Where does the Edge physically live? Magnet-mounted in the workstation case, or standing on the desk? It decides whether the Pi lives in the case too, and how far the two cables have to run.
  • Keep GRUB’s default as Linux? Keeping it preserves the Windows → Linux leg; flipping it makes cold sim starts a minute faster and breaks that leg. Only one can be true.
  • Alerts to your phone? If yes I’ll add Alertmanager and an ntfy topic in phase 4 — worth it mainly for “the Pi itself is unhappy”, since it’s the single point of failure.
