Flight Deck

A 2560 × 720 touch ribbon that boots the workstation into Windows or Linux, launches the sim, and shows what the machine is doing right now — driven by the Raspberry Pi 4B, so it still works when the workstation is off.

deck-api + SSE boot state machine cage kiosk live sparklines, in memory Prometheus Grafana Loki NVMe

The premise

A control surface, not an observability platform.

The repo already had one front-end: an Echo turns on a fake Wemo plug, fauxmo fires flightsim-boot.sh, and the script wakes, reboots, or launches into the right OS. The Edge is a second front-end onto the same machinery — plus the thing voice can never give you, which is a live picture of the ninety seconds after you ask.

It hangs off the Pi, not the workstation. The workstation is the subject of every control on this screen; a panel that goes black exactly when you reboot the machine is the one thing this can't be. The Edge takes HDMI 2.0 alongside USB-C DP-alt and its touch panel is a standard USB HID digitizer, so a Pi 4B drives it with micro-HDMI for video and USB-A for touch, with no vendor software in the path.

Everything numeric on it is the latest reading. The traces are a rolling hour held in the browser's memory, and they die with the page. Nothing is scraped on a schedule, nothing is retained, nothing is written to the Pi's thumb drive.

The ribbon

2560 × 720 — drawn at true proportion

Five-to-one is a strange canvas: almost no vertical room, enormous horizontal room. Three fixed columns — act on the left, the boot then the machine in the middle, fleet on the right — and the boot controls are never behind a tab, because reaching them is what you do while the machine is unusable. At 14.5″ this panel is ~180 ppi, so a 44 px target is a 6 mm one. Everything touchable here is 158 px or larger.

Live telemetry

The only history that exists is in the browser

Why the browser holds it

A rolling hour at a 5 s poll is ~720 points per series — a few tens of kilobytes of floats. Putting that in a time-series database would mean continuous small writes to flash with no real wear levelling, to answer a question nobody asks: what was the GPU doing last Tuesday? The panel only ever asks what it is doing now, and how it got here in the last hour.

Names are matched, not pinned

The two exporters call things different names — gpu_temperature_celsius on one, gpu_temp_c on the other — and have changed before. deck-api parses the Prometheus text format and matches on shape, so either exporter maps onto the same few panel keys, and a metric that isn't exported simply doesn't appear rather than reading zero.

Gaps are information

When neither OS answers, deck-api records nothing rather than a zero, and the trace breaks. On a dual-boot machine that gap is the reboot — the same event the phase track is narrating. Interpolating across it, or carrying the last value forward, would erase the single most interesting thing this panel has to show.

Built

Three steps, each provable on its own

StepRunProves
Prove the panel./pi/display-check.sh Connector state, whether 2560 × 720 is advertised, digitizer enumeration, RAM and thermal headroom. Read-only.
sudo ./pi/setup-display.sh cage + chromium kiosk, then a touch self-test: viewport, input type, corner registration, worst offset.
Wrap the orchestratorsudo ./pi/setup-deck.sh deck-api on :8088, fauxmo repointed at it, kiosk repointed at the real UI.
Check the logicpython3 pi/deck-api/test_phases.py The phase mapping against the exact strings the orchestrator emits, including chained-reboot and timeout paths.
python3 pi/deck-api/test_telemetry.py Exporter parsing and canonicalisation, both naming schemes, malformed input, and the no-OS-up gap.

flightsim-boot.sh is not modified. deck-api triggers it exactly as fauxmo always has and derives phases by following the script's own journalctl -t flightsim-boot output, so a boot started by voice, by touch, or by hand all render identically — and one started elsewhere is adopted when its first log line appears.

Hardware

The Pi you already have

LinkCable / partNote
Pi 4B → Edge (video)micro-HDMI → HDMI HDMI0, the port nearest USB-C. 2560 × 720 is 1.84M pixels — fewer than 1080p — so it's comfortable on a 4B.
Pi 4B → Edge (touch)USB-A → USB-C A black USB 2.0 port. HID needs no bandwidth, and this keeps both blue ports free.
Edge powerits own USB-C PD supply The 4B supplies 1.2 A total across all four ports. Don't draw the panel from it.
Pi storagethe existing 64 GB thumb drive Fine, now that nothing writes in a loop. /tmp is moved to tmpfs and deck-api state lives in /run.
Coolingfan + heatsinks Already fitted — which is what makes sustained kiosk plus polling a non-issue on a 4B.

Software side: force the mode with video=HDMI-A-1:2560x720@60 in cmdline.txt if EDID doesn't offer it — setup-display.sh --force-mode does it, backs the file up, and reverts if the edit would add a second line, since a two-line cmdline.txt is an unbootable Pi. The UI runs under cage rather than a desktop: one fullscreen surface, no panels, nothing to blank the screen.

Deliberately absent

And what it would take to change that

  • Prometheus, Grafana, Loki, long-term retention. A TSDB on flash with no real wear levelling corrupts before it dies. Dropping it is what makes the existing thumb drive a non-issue rather than a liability.
  • Grafana panels embedded in the kiosk. On a 4B the browser is the most expensive process on the box; serving numbers from deck-api and drawing them inline costs roughly 700 MB less and feels instant.
  • New exporters, SMART trends, PresentMon, Mac mini telemetry. The panel uses only the probes the orchestrator already depends on.
  • NVMe and a Pi 5. Nothing here needs either.
  • Phases 6–7. They need jarvis-greeting.ps1 to call back. POST /api/hook/greeting exists and works, the UI greys them out, and boot.observable_max keeps the panel from implying it sees further than it does. Wiring it is a two-line change on the Windows side and no API change.
