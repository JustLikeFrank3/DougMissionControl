dualbootautomationproject · design pass 3 · surfaces + cockpit

Flight Deck

One always-on 2560 × 720 screen on a Raspberry Pi 4B, with four contexts. Normally the jobContext evals wallboard. When managing machines, a control deck. When listening, a media remote. When flying, a cockpit panel — with controls that show what the simulator actually did, not what you asked it to do.

deck-api + SSE boot state machine ephemeral telemetry 4 surfaces EVALS via jobContext SIM via SimConnect Prometheus in Flight Deck NVMe Pi 5

What changed

Two additions, no subtractions

The existing architecture is the baseline and stays intact: the Pi 4B is the always-on node, deck-api + SSE is the live control path, flightsim-boot.sh is unmodified, and telemetry stays ephemeral. This pass adds a surface model — DECK, EVALS, MEDIA, SIM behind one persistent navigation strip — and an architecture for real bidirectional simulator control.

The Grafana stack is sunk infrastructure, not scope

The jobContext wallboard is already running on this Pi: k3s + Prometheus + Grafana federating AKS, five provisioned kiosk dashboards (kiosk-evals, kiosk-provenance, kiosk-cloud, kiosk-ollama, kiosk-gaming), and a wallboard-kiosk.sh that probes up{job=gpu-windows} to swap playlists by booted OS. That script is not in the repo — it lives on the Pi.

All of it stays. The earlier “no Prometheus, no Grafana” rule was about Flight Deck not introducing a metrics stack; it was never licence to remove one that already exists and works. Flight Deck integrates with the existing kiosk rather than replacing it — the playlist behaviour is preserved, the dashboards are untouched, and what changes is only that one component decides what is on screen instead of two.

Inspect the live Pi before anything touches the display

Two compositors cannot share one framebuffer, so whichever process hosts the display has to host the other's output too — and that call must come from the live configuration, not from this page. pi/inspect-wallboard.sh is read-only: it captures what launches the browser today, whether it owns tty1/DRM, Grafana's health, dashboards, playlists and anonymous-access setting, k3s and Prometheus state, and the memory actually left over. It also copies any wallboard-kiosk.sh it finds into pi/wallboard/, putting that now-load-bearing script into git for the first time.

pi/setup-display.sh now refuses to run when it detects an existing kiosk and prints that command instead — and it no longer changes the default systemd target. As originally shipped it would have started a second compositor on tty1 underneath the wallboard.

The console

A 72 px strip that never leaves

Four surface buttons at 196 × 72 px each — roughly 27 × 10 mm at this panel's ~180 ppi. No hamburger, no tiny tabs, no nesting. The strip also carries the host status that SIM mode needs to keep (OS, GPU, link, clock) and a permanent HOME escape, which means it satisfies the “persistent system status in SIM” requirement everywhere rather than only there.

Moving the wordmark and clock into the strip pays for most of its height: DECK's left rail loses its own eyebrow row, so the surface below still fits 648 px comfortably.

Sim architecture

The Pi cannot speak SimConnect — so it doesn't

This is the finding that decides the whole design. SimConnect is Windows-only. Both common wrappers (Python-SimConnect, node-simconnect) require a Windows host with SimConnect installed. The Pi therefore cannot talk to MSFS directly, and a Windows-side agent is required — which is convenient, because this repo already has exactly that pattern in windows/boot-agent.ps1 on :9107.

The agent's contract, deliberately tiny

The Pi must never attempt to load or speak SimConnect. The Windows agent owns every SimConnect interaction and publishes normalized Flight Deck state — raw SimConnect concepts do not leak onto the Pi or into the UI.

EndpointPurpose
GET /healthAgent alive, SimConnect session state, sim version, current aircraft
GET /stateThe normalized state block — nothing SimConnect-shaped
POST /command{cmd_id, control, action, value} → {cmd_id, accepted, seq}
push or pollWebSocket/SSE Windows → Pi, or short polling, for rapidly changing values
The agent is expected to disappear

It starts with Windows and MSFS and vanishes on every reboot into Linux. That is normal operation, not an error: deck-api treats loss of the sim agent as SIM OFFLINE, never as a Flight Deck failure. The strip shows SIM as no link, the sim episode closes, and the display returns to the playlist.

Why a Windows agent rather than the Pi connecting directly

node-simconnect reimplements the SimConnect wire protocol and can in principle connect from Linux over TCP once SimConnect.xml is opened to the network. It was rejected for v1 on three grounds: it is an unofficial protocol implementation whose MSFS 2024 compatibility would have to be re-proven at every sim update; it puts a Node runtime on a 4 GB Pi that is already carrying k3s, Grafana and a browser; and it moves the failure surface onto the box that has to stay up. The Windows agent uses the official SDK, sits zero hops from the sim, and matches a pattern already deployed here. The adapter boundary keeps the other option open.

The rest follow the same documented naming and units, but every one of them must be verified with the SDK's SimvarWatcher against the target aircraft before code is written — MSFS DevSupport carries live threads about GEAR POSITION not matching its own documentation, and no keyboard-macro fallback should be reached for until that check has actually been run.

Development target: Beechcraft Baron G58

A default piston twin with retractable gear whose transit is slow enough to watch, three flap detents, a GFC-style autopilot, and no autothrottle — so it exercises the capability model in both directions on day one. One aircraft, proven end to end, beats a generic abstraction over aircraft nobody has flown yet.

Keyboard emulation is the fallback, and only that

A keystroke has no state channel: it cannot be acknowledged, cannot be read back, and cannot tell you whether the sim was even focused. It is permitted only for functions with no SimConnect event or variable path, must be marked in the UI as open-loop — state not confirmed, and none of the v1 five need it.

EVALS

Reclaiming the TV, without rebuilding jobContext

This is the original reason the Edge went on the Pi, and it stays. jobContext already owns the evals, the certification logic, the judge, and the provenance gate — Flight Deck is a viewport and nothing more.

Display-state controller

ConditionDisplay state
jobContext normal / idleGrafana playlist — the existing kiosk, unchanged
boot requested, any originDECK
Windows gaming onlineDECK, or the existing kiosk-gaming playlist
sim agent appearsSIM
user selects MEDIAMEDIA
MSFS exitsprevious / default → back to the playlist

The existing playlist keeps running underneath all of it. Manual selection always wins, scoped by episode, so the screen never changes while it is being used.

What EVALS shows

Whatever the jobContext boards already show, with no reinterpretation: mean judge score and the worst entry, hallucination rate, verdict flip rate, Layer 1 smoke pass rate, active alerts, per-dimension means, CoV instability by golden entry, time since the last suite run, eval pushes by kind, runs without a provenance record, and judge ⇄ provenance agreement by bucket. Flight Deck invents no thresholds and re-derives no verdicts.

The 5:1 problem

Those dashboards were laid out for a 16:9 TV. At 720 px of height they will be cramped. The fix belongs in jobContext, not here: one more provisioned board — kiosk-edge — with the same queries in a 5:1 layout. Same data, same logic, different geometry. That is not duplication; reimplementing the judge in Flight Deck would be.

Unreachable ≠ zero

deck-api health-checks Grafana and the jobContext API independently of the embedded frame. If either is down, EVALS covers the frame with JOBCONTEXT UNREACHABLE and the age of the last successful check, rather than leaving a stale board looking current. jobContext already avoids or vector(0) so a dead feed reads “No data” — that behaviour is preserved, not papered over.

Option 3 — a thin Flight-Deck-native presentation — stays on the shelf as a fallback. If it is ever needed it reads jobContext's existing /metrics endpoint, which is Prometheus text, which deck-api already has a parser for from the live-telemetry work. Still a presentation layer; still no business logic moved.

Surface switching

Automatic, but never a fight

  • EVALS is the idle default, and the last manual choice is remembered across restarts.
  • A boot opens an episode and shows DECK — whether it came from Alexa, the panel, or someone running the script by hand. deck-api already adopts foreign boots, so this needs no new signal.
  • MSFS ready opens a sim episode. Because “ready” is a stronger claim than “process running”, it comes from the sim-agent reporting a live SimConnect session, not from a process list.
  • Simulator exit closes the episode and restores the pre-episode surface.
  • HOME is always in the strip, and a manual tap always wins.

MEDIA

Reserved, and deliberately not built yet

MEDIA is a first-class surface in the navigation from day one so the console's shape is settled, showing reserved rather than pretending to work. It will hold artwork, title, artist, transport, position and volume.

The one constraint worth fixing now, because it decides the integration: the Pi is a remote control, not the playback device. Audio comes out of the machine you are actually using — the workstation, or the Mac mini — and MEDIA commands that machine. Making the Pi an AirPlay endpoint would put the music on the wrong speakers and add an audio daemon to the node whose whole job is staying out of the way.

Scope boundary

Explicitly: none of this brings the observability stack back

ConcernWho owns itWhat Flight Deck does
Eval results, certification, judge, provenancejobContext Displays its existing Grafana boards. Stores nothing, re-derives nothing.
Metric history, Prometheus, Grafana, k3sjobContext, already on this Pi Installs none of its own — and removes none either. Pre-existing infrastructure, preserved as-is.
What is on the screen right nowFlight Deck The one top-level display-state controller, with the existing playlist running underneath it.
Aircraft stateMSFS 2024 Reads it live via the agent. Never caches it as truth, never assumes a command took effect.
Flight Deck's own telemetryFlight Deck Latest value in deck-api, 60-minute rolling window in the browser. Dies with the page.
Boot orchestrationflightsim-boot.sh Still unmodified. deck-api wraps it and follows its journald output.

The rule is about what Flight Deck introduces, never about removing what is already there. Flight Deck still installs no Prometheus, Grafana, Loki, historical database, long-term retention, NVMe requirement, Pi 5 requirement, or dashboard suite of its own — and nothing in this pass writes in a loop. The Pi's existing stack is sunk infrastructure serving the original wallboard use case and stays untouched; the scope creep to avoid would be rebuilding or expanding it to support Flight Deck.

Build order

Design approved before any simulator code

  • 0 · Survey the live Pi. ./pi/inspect-wallboard.sh, then commit the survey and the recovered wallboard-kiosk.sh. Nothing else starts until the five questions at the end of that survey are answered from real output.
  • 1 · Console shell. The 72 px strip, four surfaces, episode-scoped switching, and DECK moved under it. No new backends — this is a UI change plus a small amount of surface state in deck-api.
  • 2 · EVALS. Host the existing Grafana playlist on localhost, preserving its OS-aware selection, and add the reachability overlay. The existing kiosk's playlist logic is adopted, not rewritten, and its dashboards are not touched. Then a kiosk-edge 5:1 board in jobContext if the existing layout proves too tall.
  • 3 · Sim link, before any control. The Windows sim-agent, a SimConnect session, and one read-only value on screen. This is where the SimVar names get verified with SimvarWatcher against the Baron.
  • 4 · One control, all the way. Gear only — command, acknowledgement, TRANSIT, settled state, and the no-response timeout. Everything after this is repetition.
  • 5 · The other four, then capabilities, then the later pages.
  • MEDIA stays reserved until the SIM interaction model is proven.
Open, and worth answering before step 2

Is the Pi running this wallboard the same pi-node1 the boot orchestrator installs onto? Everything above assumes yes — the k3s naming, the Grafana on :3000, and the OS-swap probe all point that way, but wallboard-kiosk.sh is not in the repo and could not be inspected. If they are two different Pis, EVALS becomes a remote URL instead of localhost and nothing else in this design changes.
